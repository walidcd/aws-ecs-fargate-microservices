# AWS ECS Fargate Microservices

**AWS Solutions Architect - Associate Graduation Project — Project 6**

This repository presents a containerized microservices architecture built around **Amazon ECS on AWS Fargate**, with service discovery, shared session caching, secure secret handling, automated blue/green delivery, and distributed tracing.

## Architecture Diagram

![Solution Architecture](architecture.svg)

## Project Goal

The goal is to migrate a monolithic Node.js application into three independent microservices:

- **Auth Service**
- **Orders Service**
- **Notifications Service**

Each service is containerized and runs independently on **Amazon ECS with AWS Fargate**. This allows the services to be deployed and scaled separately without managing EC2 worker nodes.

## How the Architecture Works

### 1. User traffic enters through the Application Load Balancer

The **Application Load Balancer (ALB)** is the public entry point.

It uses path-based routing:

```text
/api/auth/*    -> Auth Service
/api/orders/*  -> Orders Service
```

The Notifications Service is not directly exposed to the internet.

### 2. The microservices run on ECS Fargate

The three application services run as separate **ECS services on AWS Fargate**.

Fargate provides the compute layer without requiring the project to provision or manage EC2 instances.

This separation allows each service to evolve and scale independently.

### 3. Auth Service manages authentication and shared sessions

The **Auth Service** is responsible for authentication-related operations and session creation.

Session state is stored in **Amazon ElastiCache for Redis** instead of inside a single container.

This keeps the Auth Service stateless from the infrastructure point of view and allows multiple Auth tasks to handle requests for the same users.

### 4. Orders Service handles order requests

The **Orders Service** receives order-related traffic from the ALB.

When it needs to communicate with the Notifications Service, it does not depend on a fixed task IP address. Instead, it uses **AWS Cloud Map** to discover the service dynamically.

### 5. Notifications Service remains internal

The **Notifications Service** handles internal notification requests generated by other services, such as the Orders Service.

It is not exposed through the ALB, which reduces the public attack surface.

### 6. AWS Cloud Map provides service discovery

ECS tasks can be replaced, restarted, or scaled, which means their IP addresses can change.

**AWS Cloud Map** provides a stable service name for internal communication so the Orders Service can locate the Notifications Service without hardcoded addresses.

### 7. ElastiCache for Redis stores shared session state

**Amazon ElastiCache for Redis** is used as the shared session cache.

This supports horizontal scaling because session data is not tied to a specific Auth container.

### 8. Secrets Manager keeps secrets outside the application

**AWS Secrets Manager** stores sensitive runtime configuration such as credentials or API secrets.

The application retrieves the required values at runtime through IAM-controlled access instead of storing secrets in source code or container images.

### 9. ECR stores the container images

Each microservice is built as a container image and stored in **Amazon Elastic Container Registry (ECR)**.

ECS Fargate pulls the images from ECR when starting new tasks.

## End-to-End Request Flow

A typical user request follows this path:

```text
Users / Internet
       |
       v
Application Load Balancer
       |
       +------------------------------+
       |                              |
       v                              v
  Auth Service                  Orders Service
       |                              |
       v                              v
ElastiCache Redis              AWS Cloud Map
                                      |
                                      v
                              Notifications Service
```

Example:

1. A client sends a request to the Application Load Balancer.
2. The ALB routes authentication requests to Auth and order requests to Orders.
3. Auth uses Redis for shared session state.
4. Orders uses Cloud Map to discover Notifications.
5. Notifications processes the internal request.
6. Application traces are sent to AWS X-Ray.

## CI/CD Architecture

The delivery pipeline separates source, build, image storage, and deployment responsibilities.

```text
GitHub
  |
  v
AWS CodePipeline
  |
  +----> AWS CodeBuild ----> Amazon ECR
  |
  +----> AWS CodeDeploy ----> ECS Blue/Green Deployment
```

### GitHub

Stores the application and infrastructure source code.

### AWS CodePipeline

Orchestrates the delivery workflow from source through build and deployment.

### AWS CodeBuild

Builds the container images and pushes them to Amazon ECR.

### AWS CodeDeploy

Performs the **blue/green deployment** for ECS.

A new version can be introduced as a separate task set before production traffic is shifted to it. This reduces deployment risk and allows rollback if the new version fails.

## Observability

### AWS X-Ray

**AWS X-Ray** provides distributed tracing across the microservices.

It helps follow a request across service boundaries and identify where latency or failures occur.

For example:

```text
ALB -> Orders Service -> Notifications Service
```

## Security Design

The architecture keeps the security model simple and focused:

- the **ALB** is the public application entry point;
- application containers run as ECS Fargate tasks rather than directly exposing individual services;
- the Notifications Service is internal only;
- **Secrets Manager** keeps sensitive values out of source code;
- **ECR** is used as the private container registry;
- IAM permissions should follow least privilege;
- runtime services should only communicate on the ports they require.

## High Availability and Scaling

The design supports running ECS tasks across multiple Availability Zones.

Because services are stateless where possible and session state is externalized to Redis:

- ECS can replace failed tasks;
- services can scale independently;
- multiple tasks can serve the same application;
- the ALB can distribute traffic across healthy tasks.

## AWS Service Roles

| AWS Service | Role in the Architecture |
| --- | --- |
| **Amazon ECS** | Orchestrates the three containerized microservices |
| **AWS Fargate** | Runs containers without managing EC2 worker nodes |
| **Application Load Balancer** | Routes external HTTP traffic to Auth and Orders |
| **Amazon ECR** | Stores private container images |
| **AWS Cloud Map** | Provides internal service discovery |
| **Amazon ElastiCache for Redis** | Stores shared session state |
| **AWS Secrets Manager** | Stores and supplies runtime secrets |
| **AWS CodePipeline** | Orchestrates CI/CD |
| **AWS CodeBuild** | Builds and pushes container images |
| **AWS CodeDeploy** | Performs ECS blue/green deployment |
| **AWS X-Ray** | Provides distributed tracing |

## Why This Design

This architecture separates responsibilities cleanly:

- **ALB** handles public routing.
- **ECS/Fargate** runs the application.
- **Cloud Map** handles service discovery.
- **Redis** externalizes shared session state.
- **Secrets Manager** protects sensitive configuration.
- **ECR** stores deployable images.
- **CodePipeline, CodeBuild, and CodeDeploy** automate delivery.
- **X-Ray** provides visibility across service-to-service calls.

The result is a microservices architecture that is easier to deploy, scale, and observe than a single monolithic application.
